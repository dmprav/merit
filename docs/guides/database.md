# Database schema design

Use these conventions when adding or changing PostgreSQL tables in Merit. The
[architecture](../foundations/architecture.md) defines capability ownership,
[local development](development.md#schema-changes) covers migration commands, and
the [schema helpers](../../foundation/db/src/schema-helpers.ts) supply shared
Drizzle column and constraint builders.

## Choose keys and identifiers deliberately

**Use surrogate primary keys for independent entities, and keep identifier types
and foreign column names consistent across capabilities.**

| Record kind                   | Primary key pattern                                    | Example                                                                                          |
| ----------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| User-facing URL resource      | `publicId()` (`text` generated by `merit_public_id()`) | [`funding_rounds`](../../capabilities/rounds/business/src/server/persistence/schema.ts)          |
| Internal entity or event      | `uuidPk()` (`uuid` generated by `gen_random_uuid()`)   | [`contacts`](../../capabilities/contacts/business/src/server/persistence/schema.ts)              |
| External or provider identity | Explicit `text` primary key                            | [`app_users`](../../foundation/auth/src/persistence/schema.ts)                                   |
| Ordered version or weak child | Composite `(parent_id, version)` or `(parent_id, id)`  | [`material_versions`](../../capabilities/applications/business/src/server/persistence/schema.ts) |

Never use a mutable natural key such as `email` as a primary key; use `uuidPk()`
with a `UNIQUE` constraint on the natural column instead. Name foreign columns
consistently after the table they point to (`organization_id`, `round_id`,
`case_id`, `user_id`).

## Enforce invariants in PostgreSQL

**Express state domains, numeric bounds, and tenant-scoped foreign keys in SQL
so storage rejects invalid writes regardless of caller.**

- **Closed status and kind columns:** Every `text` column with a fixed set of
  values (such as `status`, `kind`, `role`, `administration`, `purpose`,
  `delivery`, `intake_status`, or `change_kind`) must carry an explicit SQL
  `CHECK` constraint via `enumCheck(...)`, not only a TypeScript Drizzle enum.
- **Bounds and non-blank labels:** Version numbers must check `> 0`, optimistic
  revisions and list positions must check `>= 0`, and free-form status labels
  such as `decision_status` must check `length(btrim(...)) > 0`.
- **Committed money vs. unvalidated drafts:** Committed amounts use
  `moneyMinorUnits(...)` (`numeric(30, 0)`) paired with an `EUR` currency check
  and `>= 0` bound. Unvalidated in-progress user input (such as draft form fields
  inside `material_drafts` or `reviewer_drafts`) remains scoped to draft storage.
- **Tenant-scoped foreign keys:** When a child row belongs to a workspace-owned
  parent (such as `assessments` or `review_requests` pointing to
  `application_cases` and `contacts`), declare the composite
  `(organization_id, <fk>)` foreign key and omit a redundant single-column FK on
  the same columns.
- **Intentional non-FK snapshots:** Creation idempotency receipts
  (`round_creation_receipts`, `application_creation_receipts`) and historical
  membership references (`review_assignments.membership_id`) intentionally survive
  or detect deletion without a blocking FK; document exceptions beside the table.

## Index every foreign key and tenant path

**PostgreSQL does not index foreign-key referencing columns automatically; add a
covering leading index for every foreign key.**

Every `FOREIGN KEY` constraint must have a `pg_index` whose leading columns
cover the referencing columns in order (through a primary key, `UNIQUE`
constraint, or explicit `index(...)`). This keeps parent deletes, updates, and
tenant-scoped joins from sequential-scanning child tables.

## Share Drizzle builders and verify against `pg_catalog`

**Import column and constraint helpers from `@merit/db/schema` rather than
redefining local builders inside each capability.**

Keep `jsonb` limited to audit event payloads and provenance
(`details`, `provenance`) backed by domain schemas; use
relational columns for any attribute filtered, sorted, joined, or constrained in
queries.

Automated schema checks in
[database schema tests](../../app/tests/database-schema.integration.ts) inspect a
migrated database through `pg_catalog` to enforce primary keys, covering foreign-key
indexes, and SQL `CHECK` constraints on enum-like columns. Run both:

```sh
vp run @merit/db#db:check
vp run @merit/app#test:integration
```
