# Verification record

## Behavioral decisions

- Scout audits fire from merged activity instead of a lens rotation: change batches, vertical area audits, horizontal sweeps of one architecture mechanism, and verification-record audits. Thresholds, the in-flight limit and the started-run timeout live in `SCOUT_RUN_POLICY`.
- At most `check.maxRunsInFlight` scout runs (3) are in flight at once: `due` lists only as many as there is room for, and reports the rest as `deferred`. The first check after rollout, with 20 runs due, starts 3.
- `scout.ts start` marks the runs a check launches, skips runs already in flight, and refuses to exceed the limit, so overlapping checks cannot start a run twice. `due` skips started runs until `advance` clears the mark or the started-run timeout (6 hours) passes, so a crashed session is retried.
- `start` and `advance` read #219 back after writing and rewrite once on a lost update, then fail loudly; the check creates no sessions when `start` fails.
- An area that no longer has tracked files at the scan tip is never due and cannot be started or advanced.
- Filing requires executable evidence. A failing test must be reachable on its pushed branch before `proposal.ts` files, and each one goes in its own new test file so it cherry-picks alone.
- Agent findings are filed `agent:ready` up to follow-up depth 2. Designs, ambiguous findings and deeper follow-ups are filed `agent:proposed`. Depth is computed from the parent issue, or from the first `Closes #n` of a parent PR.
- The Tier 1 "tests in one slice" rule uses the scout's area definition, so tests spanning two `tooling/*` packages are Tier 2.
- `tooling/agents/scout/lenses.test.ts` was deleted with the `lenses.ts` module it tested. `axes.ts` went the same way.
