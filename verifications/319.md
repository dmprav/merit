# Verification record

## Behavioral decisions

- Only program managers (`work_on_grants`) can run or read an AI review. Row security on the AI review tables also requires a program-manager membership, so a reviewer member's connection reads no rows.
- A run needs a configured provider, workspace AI consent, an application that is not withdrawn, and a workspace that is not a demo. Otherwise the section explains which of these is missing. Turning consent off blocks new runs and keeps saved AI reviews readable.
- The model receives only the current material version and the round's current criteria. Every quote must appear verbatim, ignoring case and whitespace, in the field it cites. Any provider error, timeout (90 s), malformed reply, or unverifiable citation saves nothing.
- The provider call runs between two short transactions and holds no transaction, row lock or pooled connection. Permission, consent and withdrawal are checked again at save time.
- Each run has a run identity, unique per organization. Replaying it for the same application returns the saved review without calling the provider. Reusing it for another application is refused.
- The assistant runs slow tools (`run_ai_review`) by claim, then execute outside the conversation lock, then apply. An expired claim is never re-executed automatically.
- What a person approves is what is sent. The assistant's preview names the application and criteria versions, and binds both to the run. A run that finds either changed sends nothing to the provider and answers `conflict`, which the assistant reports as a stale action with a fresh preview. Web callers and MCP callers that name no versions keep running against the current material; MCP may send `expectedApplicationVersion` and `expectedCriteriaVersion`.
- Stop reaches the provider request through the Temporal worker: the workflow cancels the step, and the activity's signal aborts the request. The run checks that signal after the provider answers and again inside the save transaction, after the application lock and immediately before the insert, so a provider that answers late, ignores the abort, or a save that waited for the lock while Stop arrived, saves nothing and the action stays stopped. Stop is recorded at once but reaches the running worker asynchronously, so a save whose last check ran before the cancellation arrived may still commit; the review remains and the action is reported as succeeded. A stopped action whose claim lapsed without an outcome looks for a review under its run identity: one that exists makes it succeeded, otherwise it stays stopped.
- An expired claim first looks for a review saved under the action's run identity. If one exists, the action is recorded as succeeded with it and the provider is not called. Otherwise it is reported as a failed, retryable action.
- A review is stamped with the time it is inserted, after the application lock, so the order of the history is the order of commit. Prepared demo reviews keep their own dates.
- The application page does not offer a run when it is read-only or the application is withdrawn; saved reviews stay visible.
- If a web run's outcome is unconfirmed, the section says Merit couldn't confirm it rather than saying nothing was saved, because the server may still finish the run.
- The full view shows Merit AI with `date · model` at the top. The run details list comes at the end, following `RecordedAssessment`.
- A model reply is applied to the conversation while its request is still the live one, re-reading the conversation after a lost revision race. A save by anything else (for example an old stopped action settling) can no longer discard the reply or leave the request's lease live until it lapses; Stop and a new turn still discard it.
- A slow run that throws looks for the review it may have committed under the action's run identity before the action is reported: a found review is recorded as succeeded without calling the provider, none keeps the failed, retryable outcome, and if looking fails too the claim stays for expiry recovery.
- Two authorized requests with the same run identity can both reach the provider before either saves. The unique constraint keeps one saved review and both answer with it, but the material may be sent to the provider twice. This is documented, not prevented.
- `ai_review_saved` analytics carry a hashed application key and the previous run's freshness (`prior`).
