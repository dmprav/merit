# Work beside reference material

Use `ReferenceWorkspace` when a task needs reading and writing at the same time,
such as assessing an application or drafting a recommendation. It applies the
experience principle of keeping references accessible during consequential work
(`docs/foundations/experience.md#keep-people-oriented`):
the reference stays readable while the work stays in reach.

## Compose the panes

Place the workspace in a contained `ApplicationPage`. On desktop, each pane scrolls
on its own, so reading further never moves the fields or their actions. Narrow and
short screens stack the panes and link between them.

- `header` takes a compact `PageHeader` with the facts people need while working.
  Put occasional, consequential actions in its **More actions** menu instead of
  scattering buttons across the page.
- `ReferencePane` holds the material people consult. Add a `ReferenceSwitcher`
  when there is more than one kind of material, such as the application and its
  criteria. Keep the switcher in the same place when reading and editing, with
  the same labels for the same destinations. Keep each choice mounted with
  `hidden` so reading positions and unfinished input survive switching.
- Both panes always render a header bar. `ReferencePane` shows its `toolbar`, or its `label` as the
  title when there is none, so do not repeat the label as a heading in the content. Both panes use the same [frame anatomy](?path=/docs/components-dialog--docs) as dialogs: a
  header bar, one scrolling body, and a footer. The bars share one height, so their rules line up
  across the split, and both bodies start at the same distance below them. Pane headers keep
  their rule at rest because they continue the application top bar's line; footers show their edge
  only while content continues below.
- `WorkPane` holds the task. Its header is always present: it shows the `title`, or the
  pane's `label` when there is none, and holds state actions (shown only with a `title`, since an idle pane has no task to act on),
  such as closing an editor or starting an amendment. `titleMeta` keeps compact
  facts about the task beside the title, such as a due-date `Badge` and an info
  control whose popover explains who asked and who can read the work. `footer` keeps status and
  the commitment action visible; on stacked screens it stays at the bottom of the
  viewport. Choose `fill` when the child, such as a `Form`, owns its own scrolling
  body and footer.

Use `as="section"` for a work pane that is the page's main task, and the default
`aside` when it supports the reference. Supply a `WorkPane` alone when sustained
work needs this frame without reference material; it then uses the full width.

When no task is open, the work pane can summarize facts and progress without
repeating the reference material. Opening sustained editing replaces that overview
with one task. Keep its controller and draft above this presentation choice, and
restore a useful trigger and reading position on Close. Reserve dialogs for short
actions that need their own focused surface.

For a short entry task, such as accepting an invitation, use a bounded page
composition sized to its content instead of reserving a full-height workspace.

## Keep reading position and focus

Inspect substantial supporting material in the reference pane while an editor is
open. Keep the editor mounted and its actions available. Within a reference, an
explicit detail view and Back action give long assessments and history enough
reading space without covering the work with another overlay. Returning restores
the originating control and reading position. Small value pickers and bounded
forms can still use the shared dialog patterns.

`useReferenceViewport` tracks the chosen reference and restores each one's scroll
position when people return to it. The feature owns which references exist, any
URL state that selects them, and focus targets inside its content.

For list/detail navigation inside a pane, `useReadingNavigation` owns the visit
trail, heading focus, and restoration of reading position. Use `previous` to label
Back with its actual destination. The feature owns destination types and content.

The [application overview](?path=/story/features-applications-application-detail--evidence),
[recommendation editor](?path=/story/features-applications-recommendation--resume-editing),
and [reviewer assessment](?path=/story/features-applications-review-an-assigned-application--writing)
use this pattern with real feature content. Check them with long material, enlarged
text, and narrow screens when changing the shared frame.
