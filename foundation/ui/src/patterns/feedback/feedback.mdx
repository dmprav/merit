# Explain outcomes and recovery

Choose feedback by the actual result and the work that remains possible. Features
supply outcomes and recovery actions; shared controls own presentation and accessible
announcements. Confirm success only after commitment, and retain unfinished work
when an action fails.

## Match emphasis to the situation

An expected consequence in a confirmation is part of the decision's normal prose.
An unexpected side effect in an editor needs a compact warning before Save.
Neither is a submission failure. The
[confirmation pattern](?path=/docs/patterns-confirmation-dialog--docs) owns this
distinction; the [Team design guidance](?path=/docs/features-team-design-guidance--docs)
shows all three contexts using the same controls.

## Choose and place feedback

| Situation                                                         | Presentation                                                                               |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| An action's outcome, including its failure, that the screen lacks | A [toast](?path=/docs/patterns-toast--docs) through `showToast`                            |
| A failure of input that is still open, such as a form's save      | One line beside the commit action in that form or dialog                                   |
| An update needs announcing without being shown                    | [StatusMessage](?path=/docs/patterns-status-message--docs)                                 |
| A concern that stays true while the person works                  | A persistent [Notice](?path=/docs/components-notice--docs) beside the affected work        |
| The page cannot show its initial content                          | [StateMessage](?path=/docs/patterns-state-message--docs) inside the page or recovery frame |

Toasts are the default. A failure belongs beside the work only when the person's
unsaved input is right there, or when nothing else can fill the space.

Place persistent feedback beside the work it affects. Choose a Notice tone that
matches the meaning and include an explanation and useful next action. Use its
`title` for the outcome and `actions` for recovery; the notice owns their alignment
and wrapping. Story tests reject a button inside a notice's message. Keep simple failures to a short sentence.

Choose the Notice appearance by the surface it sits in and how much it holds:

| Context                                                                                        | Appearance                                                         |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| A short message inside a form or dialog: a failed save, a side effect of saving, a stale draft | `appearance="inline"`                                              |
| Page or section state, or several blocks such as a title, saved details, and recovery actions  | Default tinted surface                                             |
| Guidance on how to complete the task, with no outcome or concern to report                     | Muted description text beside the fields it explains, not a Notice |

Forms and confirmation dialogs place failures in `DialogContent.feedback`, above
the action footer and outside the scrolling body. Feedback stays visible
while the footer retains its single purpose: committing or leaving the task.
Field validation stays beside its field.

When field messages explain what needs correcting, focus the first invalid field
instead of repeating a generic validation banner. Reserve form-level feedback for
problems that cannot be assigned to one field, such as a failed save.

A [concurrent edit](?path=/story/patterns-conflict-recovery--save-conflict) or a
[change to the underlying evidence](?path=/story/patterns-conflict-recovery--basis-shift) needs an inline `ConflictBanner` above the fields while
keeping the author's own editor mounted and editable. Offer clear recovery actions (**Keep my changes**
or **Reaffirm draft…** vs **Discard & load latest**). For a form of short fields, show each
differing field's saved value beneath it with `SavedValue`, as the application details editor
does, so people compare where they edit. For longer writing, place an optional **View latest**
preview outside the warning `Notice` container so the saved content does not crowd the alert.
When access or the underlying record is gone before saving, show a
[retained draft](?path=/story/patterns-conflict-recovery--retained-draft) with `RetainedDraftNotice` and offer
**Copy draft** and **Discard draft** so unsaved writing is never trapped. The feature owns which differences matter, whether editing can
continue, and which changes require strict revision checks versus last-write-wins metadata updates.

Use accessible danger text for inline errors, consistent with field validation;
color and icons supplement the explanation. Other inline Notice tones retain
normal text contrast. A compact warning about a prospective side effect follows
the confirmation pattern's body treatment instead of implying that an operation
has already failed.

A confirmed save followed by a failed refresh retries the read quietly first. If
it still fails, a warning toast from `useToastWhile` states that the change was
saved and offers **Refresh**; the work stays available meanwhile. Never imply the write failed or
offer to repeat it. A later change made against outdated information meets the
workflow's concurrent-edit check rather than a blocked screen.
See [Notices](?path=/docs/components-notice--docs) for tone and announcement guidance.

The document root renders one `Toasts` region, which owns toast lifetime, stacking,
and announcement. Keep each message to one short sentence and at most one action.
When a controller reports outcomes as an event counter, use `useEventToast`.

For dense status columns, use a plain badge with an icon and visible label.
Lead with the state that determines the next action instead of stacking routine
and failure labels. Features own that precedence: expired invitations need a new
link regardless of earlier email delivery; active invitations with sending
problems should explain that problem instead of appearing to wait on a recipient.
The underlying delivery and acceptance facts remain distinct.

## Recover the affected work

Show failures when they affect the person's work or next decision. A background
refresh with usable content can remain quiet. Failed saves and uncertain outcomes
need feedback beside the action and must retain the draft.

Use the existing recovery view when an initial read fails, including offline.
Retry the affected read or route without reloading the document. Show progress on
the retry button and prevent repeated activation while it runs. Routine background
reads need no loading indicator. When a later page of a collection fails while
earlier entries stay on screen, [`CollectionRecovery`](?path=/docs/patterns-paged-content--docs) offers the retry as a toast and
keeps the entries usable. Dismissing the toast leaves a retry button beside the entries.

Keep workspace navigation and account controls when a page fails inside an
accessible workspace. When the workspace itself is inaccessible, use the
[application shell's recovery frame](?path=/docs/patterns-application-shell--docs)
with account controls and a return link. The interface supplies a destination the
person can access. Explain which resource is affected and keep retry or sign-in
actions beside the problem. Preserve surrounding context and unfinished work
wherever it remains usable.
