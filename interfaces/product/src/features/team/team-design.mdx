# Team: accepted design patterns

Use these states as the reference for restrained team management UI. They apply
[Merit's experience principles](../../../../../docs/foundations/experience.md)
and the shared [design language](?path=/docs/design-language--docs).
The owning [workflow](../../../../../docs/workflows/manage-team.md) defines authority,
commitment, and recovery; this page explains presentation choices.

## Choose emphasis by the task

The same invitation revocation belongs in two different contexts. During access
editing, it is a side effect of Save that someone could miss. During removal,
it is an expected part of the decision. Do not turn the removal prose into a
warning just because the editor uses one.

### Warn about an editor's side effect

Keep the count and effect visible after the fields so the administrator knows
what Save will do. “Saving revokes 1 invitation. Recipients will need a new
invitation to join” gives them the scope and the remedy. The
[many-invitation state](?path=/story/features-team-manage-team--many-affected-invitations)
keeps the same compact structure.

### Make a removal confirmation read as one explanation

Group the access and invitation effects together. Explain which work and account
details survive removal, how to restore access, and what needs handing over.
Ordinary body text lets the administrator read these consequences together. The
labelled removal button names the commitment and Cancel receives initial focus.

<Canvas of={Team.RemovalConsequences} story={{ inline: false, height: "620px" }} />

### Separate an unsuccessful action from its consequences

After an unsuccessful invitation, keep the fields and draft intact so the
administrator can retry. Put the error beside the form actions. A
removal failure uses the same feedback treatment while its consequence prose
stays neutral. A [saved change whose refresh failed](?path=/story/features-team-manage-team--saved-but-refresh-failed)
is a different result: state that the save succeeded and offer to refresh.

## Read a member or invitation row

A member's identity, assigned permissions, and ability to sign in answer different
questions. Give a [disabled account](?path=/story/features-team-members--disabled-account)
its own neutral Account value. Show an actionable consequence, such as work that
needs reassigning, where someone can resolve it. The
[long and missing identity example](?path=/story/features-team-members--long-and-missing-identity)
uses synthetic records to show how the identity column handles incomplete data.

For an invitation, lead with the state that determines the next action. An expired
invitation needs a new link. For an unexpired invitation, failed or unconfirmed
sending takes precedence over waiting for acceptance. “Awaiting acceptance”
means sending succeeded and the invitation is still open. It makes no claim
about inbox delivery. [Compare delivery states](?path=/story/features-team-invitations--delivery-states).

## Change someone's access

Show a fixed responsibility as a read-only value with the reason it cannot
change. Explain available roles inside the picker, where the administrator is
choosing between them. [Owner access](?path=/story/features-team-manage-team--owner-access)
and [role choices](?path=/story/features-team-manage-team--role-choices) show how
the shared [fields](?path=/docs/components-fields--docs) work in this context.

An unfinished edit belongs to that member. Keep **Resume editing access** in the
same row menu that opened the editor so the administrator can find it again.
[Resume access](?path=/story/features-team-manage-team--resume-access) applies the
shared [editing pattern](?path=/docs/patterns-editing--docs).
